# Handover 架构

只写**不随功能变化**的部分:拓扑、模块种类与依赖方向、权威归属、结果三态、不建什么。

具体有哪些 owner、身份怎么构成、事务怎么写、协议长什么样 —— 见对应旅程的 `design.md`。
用户能做什么、系统承诺什么 —— 见对应旅程的 `prd.md`。

## 1. 拓扑

```
浏览器 ──成员会话──► Server ──┐
                        ▲      │ 记录目标
                        │ 拉取 │ 数据库裁决
                        │      ▼
                    常驻进程 ──► agent 进程
```

- **Web 是唯一的人类界面。** 机器上的命令只做接入、保持在线、以及让 agent 提交它被授权提交的东西。
- **Server 不向常驻进程推送。** 常驻进程主动拉取,并在数据库里 claim。
- **Server 可以向浏览器推送。** 推送的内容是临时的,**不是真相**。
- Server 不启动 agent 进程。常驻进程不决定权限、不决定持久真相、不决定 claim 归属。

依赖只有一个方向:**边界依赖 owner,owner 不依赖任何边界。**

## 2. 三种模块

| 种类        | 拥有                                   | 例                                |
| ----------- | -------------------------------------- | --------------------------------- |
| **owner**   | 一类事实的词汇、纯规则、恢复错误       | 一个事实域                        |
| **adapter** | 一个具体外部进程或服务的对接           | 一个 agent 运行时                 |
| **边界**    | 组合、翻译、适配 —— **不拥有产品策略** | 持久化 · 入站传输 · 常驻 · 命令行 |

owner 模块**不导入**任何边界模块。这个方向由设计和完整 diff 的人工评审保证,不扫描业务目录来推断。

**新增一个 owner** 必须同时满足:有独立身份与生命周期 · 保护相邻 owner 表达不了的权限或并发边界 · 当前就有消费者。

**派生而非存储**:任何能从已有事实查出来的东西不建表、不建 owner。

**边界之间可以互相用。** 上面那条只约束 owner。入站传输直接调持久化里的事务是对的:一个事务的
锁序写在一个文件里,包一层在外面只有两种下场 —— 纯转发,或者把一个事务拆到两个文件里。

owner 是**纯**的,这不是风格是代价:它一旦拿到事务句柄,它的测试就全部需要一个数据库。

**一个例外,量过之后留下的:**`conversation/live.ts` 导入了 `@hono/zod-openapi`。它拥有的是
`Unkept` / `Watched` —— 同一个形状既走 `pg_notify` 又走 SSE,所以它既不能住在持久化里也不能住在
入站传输里。而给一个 schema 命名(`.openapi('Unkept')`)必须发生在**用它组合出别的 schema 之前**:
试过把命名挪到入站传输那一层,结果是生成的契约里 `Unkept` 从一个具名类型变成内联展开,客户端
少一个类型。**为了目录的纯洁去换掉产品的接口形状,是把代价付错了地方。**

## 2.1 编排该住在哪

事务的编排住在持久化边界:开事务、按锁序取锁、调用 owner 的规则、由唯一索引裁决赢家。入站传输
只做三件事 —— 声明契约、解析进来的东西、把一次调用的结果翻成状态码。

这条会烂掉,而且烂法是已知的:编排一点一点漏进路由文件,直到某个 handler 有一千行。所以它需要
一个会响的计数,而不是一句「注意」:

```
一个路由处理器按领域事实分支(而不是按一次调用返回的变体分支)= 1 次
每一片结束时数一遍
到 2 就把这类函数搬出入站传输,那时才建那一层
```

**先建层再等它被填满,和先让它漏再补,一样糟。** 计数是为了让「什么时候该建」提前决定好,
而不是留给以后争论。

## 3. 权威

- 所有 winner 由数据库决定,不由进程内锁决定。
- 事务前的预检查只改善错误体验,**不授予最终权限**。可并发变化的事实必须在锁读之后、写转移之前重新校验。
- 权威时间全部来自数据库。除非是纯计算,`now` 不穿过命令层。
- 幂等、唯一 winner、唯一性约束由唯一索引强制。**迟到的写者必须在 SQL 里失败。**
- 网络调用不在数据库事务里。先持久化提交事实,再在事务外调用并记录结果。

事务顺序(不适用时不强凑):

```
begin → 锁读权威事实 → 拒绝终态或重放 → 重新校验权限
      → 写唯一的状态转移 → 记录有后果的提交 → commit
```

跨 owner 的事务写在一个文件里,**文件头写明锁序**,所有调用方遵守同一顺序。

**每张表都记下它的行是什么时候出现的,即使今天没有读者。** 六列是这样的:`agents.found_at` ·
`agent_settings.decided_at` · `browser_sessions.created_at` · `enrolments.created_at` ·
`outputs.created_at` · `users.created_at` —— 写进去,没有任何查询选它们。写下来是因为「没人用就
删」这条规矩在别处很硬,而这六列悄悄豁免着,不说清楚下一次审查还会再问一遍。

留着的理由不是「以后可能有用」,那句话什么都能留。是这样:`repository.md` 6 那条删除纪律点名的是
**被替代的模块、旧路由、无调用的 script、生成输出、依赖、CI job** —— 它们的共同点是每一样都让下一
个读代码的人多一份要理解的东西。一列时间戳不让任何人多理解什么,而它能回答的那个问题(这行是什么
时候来的)在出事的那天问不出第二遍:删掉列容易,删掉的那些值再也回不来。

`outputs` 是唯一需要说明的一个:它同时有 `created_at` 和 `updated_at`,而只有后者被读(选出来叫
`writtenAt`,也用来排序)。两列答的是两个问题——第一次写下和最后一次改动——今天的界面只问了后一个。

### 3.1 为什么规矩住在数据库里,而不是在应用层

有人反着做,而且是做同一个产品的人。[Multica](https://github.com/multica-ai/multica)(把活派给 coding agent 当同事,Go + Postgres,和我们同一件事)把它的头号数据库规矩写成:

> **Never add database foreign keys or cascading actions.** Enforce relationships and perform dependent cleanup explicitly in the application layer.

**我们不跟,理由是数出来的,不是喜好:**

```
takeOne 的竞态          两个实例同时给一台机器派活。时序测不出来 —— 唯一部分索引挡住的
最后一个 owner          退出、移除、降级三条路都能触发。延迟约束挡住的
机器和批准人不一致       复合外键挡住的
被移除的人还在被回答     一条扫全库的机械规则挡住的(不是数据库,但同一个道理)
```

四条里有三条是**多个写入者**的规则。一条规则只要有第二个写入者,由代码守就一定会漏 —— 漏的那天不报错,只是安静地不对。

**他们那条规矩解决的是我们没有的问题**:930 个迁移文件的在线迁移、多租户的批量删除。外键在那个规模上是迁移的枷锁。我们不在那个规模,而且大概率永远不在。

**什么时候该重新想这件事:** 一次迁移因为外键锁表而做不了的那天。到那天,代价的天平才真的翻过来。

## 4. 结果三态

```
succeeded   确定成功
failed      确定失败,重试安全
unknown     不知道,重试可能重复外部后果
```

- 任何外部调用**拿不到确定信号就是 `unknown`**。协议终态、进程退出、对方空闲,都不单独证明成功。
- **`unknown` 永不被猜成前两者,永不自动重放。**
- 重试由人显式发起,且**一次重试授权只能被一个后继执行消费**。
- 未提交的模型输出不是真相。它可以被显示,但不落库。

## 4.1 浏览器上谁拥有什么

```
Router        地址、参数、导航,和进入一块屏幕之前该先有什么
React Query   全部服务端状态。一个 Space、一段对话、机器列表、Inbox —— 都是它的
useState      只有这块屏幕自己的:输入框里还没发出去的字、开着的抽屉、选中的那一行
SSE           不写状态。它只做两件事:告诉 React Query 去重拉,或者喂给一个不落库的临时视图
```

Router 通过 context 拿到**同一个** `QueryClient`,guard、loader 和页面不各读一个模块单例。
loader 要首屏事实时,只负责让 Query 的同一条 query 先有答案,不另建一份 router 自己的真相。

**服务端状态不许有第二份。** 一个 `useState` 装着从接口拿来的东西,就是同一个事实的第二个家 ——
它不会报错,只会在某次刷新之后和真相不一样,而没有人知道该信哪一个。

**SSE 推来的东西不是真相**(§1),所以它不能直接变成 React Query 的缓存内容;它要么说"变了,去
重拉",要么进一个明确活不过这一轮的视图(`Watching` 就是后者:thinking 和命令全文只在这里出现,
永远不落库)。

**一条流式片段的代价,不能跟着对话长度涨。** 一轮在跑的时候,命令打印的东西每三千字节就是一次
React 更新。这一片和一小时前说过的话没有任何关系 —— 但只要 live 状态穿过 transcript 传下去,每
条已完成的消息就会跟着重渲染,并且重新跑一遍 remark。量过:40 条回复的对话,一个片段触发 80 次
markdown 解析;120 条时是 240 次。修完是 0 和 8。守它的是
`features/conversations/streaming-cost.spec.tsx`,数的是解析次数而不是耗时 —— 耗时是这台机器的事,
次数是这个 bug 的形状。

做法是所有人都会走到的那条:
[Vercel AI SDK 的 cookbook 把 markdown 分块 memo](https://ai-sdk.dev/cookbook/next/markdown-chatbot-with-memoization) ·
[Streamdown 整个库就是为这件事存在的](https://streamdown.ai/docs/memoization) ·
[LibreChat #13576](https://github.com/danny-avila/LibreChat/pull/13576) 就是同一个症状。
我们比他们简单,因为**我们流的不是 markdown** —— 流的是命令输出,进 `pre`,所以一条消息要么已经
完成要么还没到,没有半解析的块要留。

**实时流每一帧都重新问一次成员资格,这也是一个决定。** 一次带索引的查询,每三千字节的流式输出、
每个观看者一次。试过改成「最多两秒问一次」,下一次 `pnpm check` 就红在
`server/live-api.spec.ts` 的 **closes an open stream when its membership is revoked** 上 —— 那条
承诺是被机械化过的,因为它一旦坏就是安静地坏。**拿别人的保证去换速度是错的交易。** 又便宜又准确
的版本不是更慢的时钟,是没有时钟:`removeMember` 在那些瞬间已经在走的那条通道上说一声,流听见自己
的名字就关掉。等它真的出现在 profile 里再做。

**不做列表虚拟化,这是一个决定,不是遗漏。** DOM 结点数跟着 transcript 涨,而
[TanStack Virtual 专门为聊天写了一页文档](https://tanstack.com/virtual/latest/docs/chat),说明它可
做:`anchorTo: 'end'`、`followOnAppend`、`overflow-anchor: none`。不做的理由是
[它自己那篇文章的标题](https://tanstack.com/blog/tanstack-virtual-chat)——聊天把普通列表的契约反过来
了:新内容在末尾长、历史往开头插、最后一条还在逐字变。换掉现在这个能正确锚定滚动的原语,去换一
个手工管理偏移的,是拿一个没量到的问题去换一个已知很难的问题。**重新想它的触发条件是:有人真的
因为一段对话太长而卡住。** 到那天,先量 DOM 结点数,再谈。

[Multica 把同一条写成硬规则](https://github.com/multica-ai/multica):React Query owns all server
state · Zustand owns client/view state · WS events update React Query。我们没有 Zustand,那一半是
`useState`,其余一样。

依赖方向是 `main → routes → features → api/generated/components`。route 把地址翻成 feature 的输入,
feature 不反过来导入 route;跨 feature 的共享值只有真共享时才下沉,不靠互相导入页面文件建立环。

## 5. agent 的边界

- 具体 adapter 拥有进程生命周期、原生协议、临时目录清理。**不为对称暴露共同的生命周期接口。**
- adapter 声明自己支持哪些能力。请求一个它不支持的能力**响亮失败**,不接受了再忽略。
- agent 只获得当前这件事所需的有界上下文,也只能改变当前这件事的事实。
- agent 不持有人的凭据,**没有绕过它所在的常驻进程直连 Server 的路径**。

## 6. 明确不建

Event Sourcing · workflow 引擎 · provider/model registry · 通用 session owner
参与者 owner · 通知 owner · 调度 owner · 跨 owner 的 helper 模块
把某个 agent 协议当成核心 wire · 把版本库当成事实的身份
