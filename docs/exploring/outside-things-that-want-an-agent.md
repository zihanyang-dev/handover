# 外面的东西想让 agent 干活

> 调研于 2026-08。**没有决定,没有建。** 这里引的产品都在动,真做的时候要重查。

## 要回答的问题

以后想接 GitHub 的 PR 评论、issue、监控告警……这些东西进到系统里,

1. **一件活归谁?**
2. 一个 PR 的第一条评论让 A 干了,第二条评论来了,难道跑去 B?
3. 一个全新的事件进来,怎么选 agent?
4. 一万个平台,数据库怎么建才不会变成一万个字段?

问题 1 是最要紧的,因为 `tasks.owner_user_id` 是 `NOT NULL` —— **每件活都必须有一个人在钩上**。
`04` 就是为此设计的:agent 开的子任务,owner 是它的父任务,所以它的提问不进任何人的 Inbox。一件
owner 空着的活,卡住的时候没有人收得到它的问题。

---

## 查到了什么

### 一、后续事件不做选择,因为外部那个东西就是一段对话

[daily.dev 写他们做 Linear coding agent 的「难点」](https://daily.dev/blog/how-we-built-a-linear-coding-agent-the-hard-parts)
时提到:他们加了一张 SQLite 表,把 `(issueId, continuityType, provider)` 映射到 Claude/Codex 的
session id —— 计划、实现、审查、开 PR 全部复用同一个 session,「**它记得自己计划过什么,而这在它
审查自己代码的时候很重要**」。

所以第二条评论回到 A,不是因为谁「选」了 A:**它根本不是一件新事**,是同一段对话的下一行。

这对我们几乎是白送的。`03` 已经定了「一段对话终生绑定一个 agent、一台机器」,
`conversations.agent_session_id` 已经在了。缺的只有一张映射表。

**一个顺带的验证:** 同一篇文章说他们踩到「Claude Code 的 session 查找键里包含工作目录」,分阶段
在不同目录跑就静默失败。这正是 `07` review 第二轮找到并修掉的那个 bug —— 子任务干完之后人再往里
说一句,会解析到另一个文件夹。我们现在是**一段对话终生一个目录**,天然免疫。这条别再改回去。

### 二、第一个事件:没有人做自动路由

特意查了四家,想找一个「系统自己决定派给谁」的做法。**一家都没有:**

```
GitHub Copilot            把 issue 指派给 Copilot,像指派给一个人
Claude Code GitHub Action 在评论里 @claude(触发词可配)
Devin                     指派 / @devin / 打一个 devin 标签
Linear                    把 issue 指派给 agent
```

四个独立的产品,同一个答案。推测原因:**真正难的不是「选哪个 agent」,是「该不该让 agent 碰这件
事」**,而后者到今天没有人找到一个人们敢信的自动答案。

### 三、归谁:人仍然是 owner,agent 只是被委派

[Linear 的文档](https://linear.app/docs/agents-in-linear)把这句话说得最清楚:把 issue 指派给
agent 是**委派**给它,**而那个人类队友仍然是主负责人和 owner**。

和我们的地基是同一句话。

### 四、告警是另一回事

告警没有线程、也没有人点名。[ops 那边的做法](https://www.augmentcode.com/guides/ai-agents-incident-management)
要么是人事先写死的路由规则,要么是**升级给人批**——高置信度才自动处置,含糊的一律要人点头。

## 得出的结论

### 归一化之后只有四样东西

不管是 PR 评论、工单、Slack 线程还是告警,穿过边界之后我们只要:

```
① 关于哪个外部东西    来源 + 一串不透明的 id,我们从不解释它
② 谁                 他在那边的身份 → 我们的人
③ 说了什么            一段文本
④ 有没有点名一个 agent
```

**每个平台都是这四样。** 平台特有的知识全部留在边界外面。

### 于是四个问题的答案

```
后续事件      查 ①,进同一段对话,不做任何选择
新事件        看 ④。没点名就不开活
归谁          ②。谁点的名,活就是谁的 —— 解析不出就拒绝,不猜
一万个平台     见下
```

「谁点的名谁负责」不是为了省事:它让「它卡住了要问人」有一个明确且正确的收件人 —— 当初要它干活的
那个人。②解析不出来时**必须拒绝而不是找个人塞进去**,因为 owner 猜错的活,它的提问会掉进错的人的
Inbox,而那个人不知道自己该回答什么。

### 一万个平台:三列文本,和平台数量无关

```
来源      'github' / 'linear' / 'sentry' / 随便什么
外部 id   那边那个东西的 id,不透明
对话 id   我们这边的
```

接第一万个平台,这张表还是三列。

**这个仓库已经有这个先例:** `credentials` 表是 `kind` + `subject` —— email 的地址、Google 的
sub、GitHub 的 id,三种完全不同的东西共用两列,表本身不知道 `subject` 是什么意思。加一个身份提供方
不改表。

同样地,**每接一个平台多的是一个文件,不是一个字段** —— 和 `AGENT_KINDS` 加一个 agent 一样。适配器
里装的是每家都不同的那些事:验签、去重键的来源(有的给 delivery id,有的给 fingerprint)、以及从
它那坨 JSON 里挑出上面那四样。

**不存原文。** 翻译不出来的、我们不关心的事件类型直接丢掉并返 200,和 `agentsFound` 丢掉不认识的
命令是同一个判断。但要和「我们自己坏了」分开 —— 后者返 5xx 让对方重试。两者混成一个,要么被一个
根本不关心的事件类型反复重试打爆,要么静默丢掉本该处理的。

### 告警不直接开活

理由不是新的,是 `07` 已经写下的那条:**「没有人在场的时候,不该有人的电脑被调度。」** 我们用它禁掉
了 agent 点名别人的机器。凌晨三点的一条告警是完全一样的情形。

所以告警进 Inbox(「这个响了,要不要派个 agent」),或者命中**人自己事先写下的规则**——那本质上是
同一件事,只是提前授权了。

于是整个系统保住一条不变量:**活只由人创造,直接地,或者通过他自己事先写下的规则。**

### 落到文件上

```
server/<来源>-api.ts   入站 transport,一个来源一个文件,anyone() 那道门(已有先例)
incoming/<来源>.ts     翻译:它那坨 JSON → 那四样东西。不碰 SQL
db/conversation.ts     不动。人用的那两个动词已经够了:
db/task.ts             一条消息进已有对话,或者开一段新对话并交办
```

正好是 `code-style.md` §6 那三类模块。不需要队列 —— 这个系统已经有一个了:`turns` 加机器自己的
轮询,`pg_notify` 唤醒。

## 还没有答案的

**第三种调用者。** 今天进得来的只有浏览器会话和机器凭据(`route.ts` 里就那几道门)。「一个第三方
系统」这种调用者完全不存在:没有 API key、没有 scope、没有「代表谁调用」。**这是真正的前置条件**,
而且它和 [A2A](a2a.md) 卡在同一个地方。

**那张连接表长什么样。** 我们和那边哪个账号连上了 —— GitHub App 的 installation、Linear 的
workspace、Sentry 的 org,每家概念都不同。猜测还是 `credentials` 那个形状(`space_id` + 来源 +
不透明的账号 id + 密钥),但没细想过。

**②怎么解析。** 那边的身份 → 我们的人,这张映射是怎么建立的?让人在设置里绑一次?还是从已有的
`credentials`(已经有 `github` 这个 kind)推?没查。

**顺序。** 我认为这一片排在「它做完了会来找你」后面:一个连**人**都叫不回来的系统,先去支持外部
系统派活是反的 —— 你半夜被 issue 触发跑了三件活,第二天早上还是没人告诉你。
