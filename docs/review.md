# Handover 评审

**给执行评审的 agent。**

评审是**读代码**。命令只回答「该看哪里」,不回答「对不对」——
**命令的输出为空,不等于通过。** 每一处判定都来自读完那段代码本身。

三件事分开:

```
怎么读     七个阅读动作            第 2 节
拿什么量   五个维度                第 3 节
什么时候   改动评审:三遍           第 4 节
           里程碑:全项目审查       第 5 节
```

拥有:上面这三件。不拥有:美学规则(`code-style.md`)、命令(`repository.md`)、架构不变量(`architecture.md`)。

---

## 0. 硬规则

```
1  没有证据的发现不报告。证据 = 复现路径,或一次真的失败的测试。
2  不确定的进 UNVERIFIED,单列一栏,不要混进发现里。
3  不报没有失败陈述的条目。失败陈述 = 具体输入 → 具体的错误结果。
   "可以考虑" "建议优化" "更好的做法是" —— 一律不写。
4  每一条新断言必须红过(2.7)。没红过的断言等于没有断言。
5  发现之后不要顺手重构。只改这条发现指向的东西。
```

---

## 1. 先写事实清单

**这次改动动了哪条不变量,一到三条。写不出来就不要开始读。**

```
<名词或规则>: <旧> → <新>

真实例子:  机器的归属: Space → 人
```

这张清单决定**读的顺序**:先读这条不变量最集中的那个函数,再顺着它往外走。
**不要从上往下读 diff** —— diff 按文件排,不按意思排。

---

## 2. 怎么读:七个动作

### 2.1 先自己复述,再看它自称做了什么

```
读函数体,先不看函数名、不看注释,自己说一遍它做了什么。
然后读名字和注释。
两者不一致的地方,要么是 bug,要么是烂名字。二者必居其一。
```

**最重要的一个动作。** 注释是「作者以为的」,代码是「实际发生的」——
而读的时候注释就在旁边,它会替你把结论想好。所以顺序必须是先自己说,再看它说。

> 真实命中:注释写着「锁住这台机器」,而代码是 `innerJoin(memberships) + forUpdate()` ——
> `FOR UPDATE` 锁 `FROM` 里的每一张表,**`memberships` 那行也被锁了**。
> 于是「开一段对话」排在任何动成员资格的事务后面。注释没提,因为作者没想到。

### 2.2 顺着一条真实输入走一趟,不顺着文件走

```
挑一个具体输入:一个真实的 HTTP 请求、一条真实的 CLI 命令。
从入口走到落库为止,或走到变成响应为止。
每一个分支都要说出「另一支会怎样」。
```

按文件读会漏掉**跨文件的半截改动** —— 每个文件单看都自洽。

> 真实命中:归属改人之后走「生成一把钥匙」这条路,走到 `POST /spaces/{slug}/machine-keys`
> 发现它还挂在成员门后面 —— 而它生成的钥匙已经不带 Space 了。

### 2.3 每读一个「读」,问它读的是账还是记录

```
账(turns / tasks / machines)   封闭取值,数据库裁决,可以用来判断
记录(messages / 事件流)         开放取值,给人看的,不能用来判断
```

**判断永远不读 transcript。** 看到 `if` 的条件来自消息内容、来自「最后一条」、来自事件类型 —— 停下来。

### 2.4 每读一个「写」,问三件事

```
谁能触发它?          门在哪,门管的是不是这次真正要保护的东西
同时来两个会怎样?    守卫是 where,还是先读后判断?后者两个都会过
中途失败留下什么?    半截状态能不能被下一次请求看见
```

### 2.5 读被改函数的全文和它的调用方,不读 hunk

diff 的上下文行给的是**行的邻居,不是意思的邻居**。每个被改的函数读完整定义,再逐个打开调用方:
门 · 路径 · 返回码 · 失败文案 · 客户端 · 测试夹具 · prd · design · 迁移的 down。

### 2.6 读「没了什么」,不只读「多了什么」

眼睛会自动读 `+` 行。两类要单独看:

**丢掉的行为** —— 改动本身是对的,而某句话是顺手没了的。

> 真实命中:归属改人之后,connect 页那句「你还没有 Space」被顺手删了。接进来仍然成功,
> 但没有地方能跑;事后才发现,看起来像机器坏了。

**变松的断言** —— `toEqual → toMatchObject` · `toBe → toBeDefined` · `toBe(n) → toBeGreaterThan(0)`。
放松必须有一句写在测试里的理由。没有理由的放松就是把一条保护删了。

### 2.7 对每条断言,亲手让它红一次

```
1  改坏它保护的那一行:删一个 where · 把 orderBy 反过来 · 把返回值写死 · 去掉兜底
2  pnpm exec vitest run <这个 spec>
3  确认它红,而且红在预期的那句 expect 上 —— 不是超时,不是别的测试连带红
4  改回来,确认绿
```

**红的原因不对,等于没红。** 这是 agent 评审里唯一挡得住「看起来对」的装置 ——
推理再顺也可能是假的,一次红是真的。

## 3. 拿什么量:五个维度

**动作说怎么读,维度说用什么尺子。每一遍都带上全部五把尺子。**

### 3.1 架构

```
这个事实的 owner 是谁?改动有没有让第二个地方也拥有它?
判断读的是账还是记录?
能从已有的东西推出来的,有没有被存下来?
依赖方向对吗?编排住对地方了吗?(architecture.md)
```

> 违反长什么样:在 `machines` 上存一列「能在哪些 Space 用」——
> 那是「谁在哪个 Space」的第二份拷贝,而它和真的那份不一致的那天,没有任何东西会说一声。

### 3.2 逻辑

```
0 / 1 / n:结果不唯一时选的是哪一个?每次都是同一个吗?
并发:两个同时来会怎样?
失败一半:留下的半截状态,下一次请求看得见吗?
每个错误有不同的恢复动作吗?同一个恢复动作是不是被拆成了两个错误?
```

> 违反长什么样:交办按名字找机器,两个人都把笔记本叫 `mbp`,而查询没有 `orderBy` ——
> 同一个名字每次可能指向不同的机器。

### 3.3 产品

```
人要做的动作,变多了还是变少了?
人需要先理解系统才能用吗?
失败的时候,人知道下一步做什么吗?
代价落在谁头上?
有没有要求人去机器上装东西、记东西、粘东西?   ← 硬约束,命中即阻断
责任还有名字吗 —— 谁交出去,谁交回来?
```

> 违反长什么样:在别人的机器那一行上放一个「断开」按钮,按了会失败。
> **提供一个按了会失败的按钮,比不提供更糟** —— 它读起来像是你可以做的事。

### 3.4 简约(less is more)

**这是最容易被绕过的一把尺,因为加东西永远有理由。**

先数。六样东西,每一样都要能报出改动前后的数字:

```
用户要学的名词      加一个,所有人永远要学它
状态                n 个状态就有 n² 条边要说清楚
问人的问题          每多问一个,就是把我们能推出来的东西推给他
存下来的事实        能派生的不要存 —— 存了就有两份,就会不一致
做同一件事的路      一条。第二条通道是最贵的那种"多"
命令 / 接口         同一件事不要两个入口
```

**数字只要涨了,就必须过下面这一关。每一条都要能答出来:**

```
删掉它,谁在什么具体的事上具体地失败?    答不出 → 删(AGENTS.md 的失败陈述)
它能不能从已有的东西推出来?              能 → 不该存,也不该问
已经有一条路能做到这件事了吗?            有 → 不加第二条
这个状态有哪几条进边、哪几条出边?        说不全 → 这个状态不该存在
用户必须学这个新名词吗?                  必须 → 升级给人,不要自己决定
```

> 这个项目真实砍掉过的:
>
> ```
> 状态从六个砍到四个    working / wait / sleep / done
>                       「在等子任务」不是状态,是数出来的
> ending 整个删掉        说不出它的进边和出边
> 六个事件接口合成一个    它本来就是一条 SSE
> new 一条命令两种用法    提给人和交给 agent 是同一件事,区别只在给谁
> 四个动词就是四个状态名  --help 就是那张状态图,不用在 prompt 里再解释一遍
> 可达性是 join 不是列
> 不问「进哪个 Space」    那个答案本来就跟着成员身份走
> ```

**反过来的守则:less is more 不是「代码写少」。** 为了少一个字段而让读代码的人多推三步,
是更多,不是更少。**判据是别人要理解的总量,不是行数。**
同理:注释可以长(`code-style` 11),因为它减少的是下一个人要重新推的量。

### 3.5 美学

规则由 `code-style.md` 拥有。评审只带三个问题,因为它们能被答错:

```
这个名字是领域里的词,还是实现的词?
   reachableFrom ✓   machinesJoinMemberships ✗
   waitingRoom   ✓   pendingRequestManager   ✗

这个函数是不是一个抽象层?有没有一半在讲策略、一半在拼字符串?

这条注释删掉之后,半年后会不会有人把它改回错的?
   不会 → 这条注释是废话
```

## 4. 改动评审:三遍

**每一遍的输入不一样,所以不是把 diff 读三次。五把尺子每遍都带。**

```
第一遍  能不能用    输入:事实清单指向的那些函数的全文
                    动作:2.1 · 2.2 · 2.3 · 2.4 · 2.5
第二遍  是不是真的  输入:- 行,和所有新增/改动的测试
                    动作:2.6 · 2.7,外加 4.1
第三遍  值不值      输入:文档、注释、用户看得见的文案
                    动作:4.2,并把 3.3 / 3.4 从头再问一遍
```

顺序是内容:**架构错了,底下的整洁全是白做的。** 先抠文案再发现锁拿错了,前一遍白读。

**自评唯一的失败模式是「我知道我想干什么」。** 分遍是强制换视角的装置 —— 换问题,不是再看一遍。

### 4.1 测试的名字 vs 测试的身体

```
对每一个新增的 it(...):把名字里的名词列出来,逐个到身体里找。
名字说的每一个东西,身体里都要真的建出来。
```

> 真实命中:`says whose it is, because one of them is somebody else's laptop` ——
> 名字说「其中一台是别人的」,身体里只建了自己的一台。它通过 CI,而它保护的东西不存在。

顺带三问,答案都要是「是」:换操作系统还测同一件事吗?以 root 跑还成立吗?不靠 sleep、顺序、时钟吗?

> 真实命中:用 `/proc/nowhere` 表示「写不进去的地方」。macOS 上没有 `/proc`,它是**因为路径不存在**
> 而失败;Linux runner 上 `/proc` 是真的,递归 mkdir 卡住,5 秒超时。
> 改成「拿一个普通文件挡在目录该在的位置」——`ENOTDIR`,所有平台一致,对 root 也成立。

### 4.2 文档和注释里的断言会变假

**带「一定 / 永远 / 不影响任何事 / 只能」的句子,每次都要重新判一遍。** 没有工具会告诉你它变假了。

> 真实命中:prd 写着「两台机器同名不影响任何事」。而交办正是按名字找机器 —— 这句已经是假的。

注释更隐蔽,它常引用一条**约束名**。迁移里 drop / rename 掉的每一个约束、索引、列,拿名字去搜源码 ——
指着不存在的东西的注释,读起来仍然完全合理。

## 5. 里程碑:全项目审查

**没有 diff,也没有事实清单。** 输入是整个仓库、四份稳定文档,和上一次里程碑的审查产出。

改动评审找的是 bug;**全项目审查找的是熵** —— 每一条单看都不算错,合起来让这个仓库变难。

按顺序走七项。每一项都要报**数字**,而不是「看起来还好」。

```
① 并存的旧路径
   同一件事有没有两条路能做到?
   方法:对每个用户可见的动作,列出所有能做到它的入口(路由 · CLI 命令 · 直接写库)
   应该只剩一条。多出来的那条,是上一次「改一半留着旧的」留下的。

② 派生与存储的漂移
   存下来的事实里,有哪些其实能从别处推出来?
   方法:逐张表看列。问「这一列和哪张表里的什么东西说的是同一件事」
   命中的:要么删掉存的那份,要么写清楚为什么必须存(缓存要有失效路径)

③ 死的东西
   没有调用方的导出 · 没人引用的文档段落 · 永远为真的分支 · 从来不红的测试
   方法:导出逐个 grep;测试用 2.7 抽样让它红一次
   删。不是标记为废弃,是删。

④ 名词的分裂
   同一个东西在代码 / 接口 / 文档 / UI 文案里叫不同的名字
   方法:列出用户可见名词表,每个名词到这四个地方各搜一遍
   分裂的名词是最贵的熵 —— 它让每一次讨论都要先对齐词

⑤ 文档与代码的漂移
   每份 prd 的承诺,逐条到代码里找证据。找不到证据的承诺,不是"还没做",是"文档在撒谎"
   四份稳定文档 + 每一片的 prd / design,全过一遍 4.2

⑥ 机械化的覆盖率
   上一次里程碑说要机械化的,做了吗?
   这一段时间里重复出现过的同类发现,有几条还在靠人看?
   目标是这个数字每个里程碑都在降

⑦ 清单还是定长的吗
   AGENTS.md 说最多 8 条。现在几条?每一条还能写出它的失败陈述吗?
```

跑一次真的:

```bash
pnpm check
pnpm test:agents      # 真的 claude 和 codex,花真的模型调用
```

再把当前里程碑最主要的那条旅程,**用真的二进制、从人的那一端走一遍**。
假 agent 测不出的东西,只有跑真的才抓得到。

### 5.1 全项目审查的产出必须包含一份删除清单

```
## 删除
- <删掉的东西> — <为什么它不再需要存在>
```

**可以为空,但为空必须解释:这一段时间里为什么没有产生任何可删的东西。**

熵只会增,不会自己减。一次只加不减的全项目审查,等于没做。

## 6. 每条发现的处置

```
修          这次就改。只改这条指向的东西,不顺手重构。
机械化      变成一条 lint 或一个测试,以后不用再评审。
升级给人    命中 AGENTS.md「升级给人」的,先问,不要自己决定。
            —— 新 owner、新的用户可见名词、改公开协议、外部后果、和已冻结文档冲突
```

**优先机械化。** 每条发现都问一句:这条能不能变成测试或 lint,让它以后永远不用再读?
按 `code-style.md` 0 的标签归位:`lint` / `test` / `gen` / `人工`。

已经机械化的例子全在 `apps/server/src/server/app.spec.ts`:`/machines/current/…` 必须出示机器凭据 ·
`/me` 和 `/spaces` 必须出示会话 · Space 内的路由必须能答 404 · 不出示任何东西的路由是一张手改白名单。
改路由那次,最后一条**自动逼着**更新了白名单,没有人需要记得。

上一个项目量过:机械化了的规则违反数 0;没机械化的那一条,积了 365 处。

不能机械化的,写进**拥有这个事实的那份文档**。评审记录进 Issue,不进仓库。

## 7. 命令附录:只用来定位

**这些命令给候选,不给结论。每一条命中都要打开那段代码,按第 2 节读完再按第 3 节判。**

```bash
BASE=$(git merge-base origin/main HEAD)   # 一批提交
BASE=HEAD                                  # 工作区
```

```bash
# FOR UPDATE 会锁 FROM 里的每一张表,包括 join 进来的
for f in $(grep -rl "forUpdate()" apps/server/src --include="*.ts" | grep -v spec); do
  awk -v F="$f" '/selectFrom|updateTable/{j=0} /innerJoin|leftJoin/{j=1} \
    /forUpdate\(\)/{ if(j) print F":"NR }' "$f"
done
```

读完判的是**被 join 那张表的锁是不是承重的**:

```
承重    它就是某条保证的实现 —— 留下,并在注释里写明为什么锁它
        例:machineSays 锁 machines,是「移除之后不能再写进一行」的实现
不承重  要它的列就 .forUpdate('主表');只当条件就换成 where exists(...)
        例:reachableFrom 锁 memberships,纯属 join 的副作用
```

```bash
# 通知与事务
grep -rn "pg_notify\|wakeMachine\|noteWritten" apps/server/src --include="*.ts" | grep -v spec
```

读完判的是**这条通知描述的是不是一行刚写下的数据**:

```
是   必须拿 tx。拿 pool 发出去的可能先于那行到达,被叫醒的一方看不到东西,回去继续等
否   拿 db 正确 —— 通知自己就是全部内容,没有任何行能比它先到
     例:live 流里那些不落库的瞬间
```

```bash
# 结果不唯一时选了哪一个
git diff $BASE --name-only -- 'apps/server/src/db/*.ts' | xargs grep -n "executeTakeFirst()"

# 迁移动过的约束名,拿去搜注释
git diff $BASE -- 'apps/server/migrations/*' | grep -E "^\+.*(drop|rename|add) (constraint|index|column)"

# 变松的断言
git diff $BASE -- '*.spec.ts' '*.spec.tsx' | grep "^-.*expect("

# 丢掉的行为
git diff $BASE -U0 | grep "^-" | grep -v "^---"

# 一条不变量的所有引用点
grep -rn "<旧名词>" apps packages docs | grep -v "/generated/\|/dist/"
```

## 8. 收尾

```bash
pnpm check
```

逐条回答:

```
每个被改事实的 owner 是谁?
happy path 是否线性?
不同恢复是否有不同错误?同一恢复是否没有同错仪式?
字面量是否只携带调用方拥有的事实?
事务阶段是否可见?
有没有重复或转发?
这个节点是否删除了它替代的东西?
有没有直接证据显示这条旅程真的跑过?
```

## 9. 产出格式

```
## 发现

1. <一句话说清缺陷> — <文件:行> — <哪个维度>
   触发:  <具体输入 / 具体并发时序>
   结果:  <具体的错误结果>
   证据:  <复现路径,或那次红了的测试和它红在哪一句>
