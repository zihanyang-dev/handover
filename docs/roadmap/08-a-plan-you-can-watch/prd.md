# 08 · 一份看得见的计划

## 为什么

交给 agent 一件多步骤的事,现在能看到的是一串正在发生的动作:读了这个文件、跑了那条命令。
**看不到的是它打算干什么。** 一分钟前它说"planned 7 steps",那七步是什么、走到第几步了、
中途有没有改主意 —— 全都没有。

这不是缺一个装饰。人把活交出去之后唯一的问题是「它在正确的路上吗」,而回答这个问题需要的
不是最近一条动作,是**那份计划,以及它走到哪了**。

`claude-code.ts` 里那行注释早就把话说完了:

> A count, not a list: **a plan belongs on the page as a plan**, and this line is only meant to
> say that one was made.

这一片就是把那句话兑现。

## 决定

### ① 计划是它自己写的,不是我们要来的

两个 agent 本来就在做这件事,而且形状几乎一样:

```
Claude Code   TodoWrite     todos[]  { content, status: pending|in_progress|completed, activeForm }
Codex         turn/planUpdated  plan[]  { step,  status: pending|inProgress|completed }
```

**三态一致,而且都是每次发全量而非增量。** 所以「中途改计划」在两边都是「再发一次完整的
计划」,天然幂等 —— 我们不需要发明合并规则,也不需要教 agent 怎么规划。

不做的事:不要求 agent 先出计划再干活。那是 harness 该管的,不是这里。它给了我们就显示,
不给就没有 —— 一个不出计划的 agent 不该因此变得不能用。

### ② 每次变更都进转录,当前计划靠推导

计划的每一次变更是**一条活动**,和"它停下来问了个问题"、"它把活交回来了"同一类。理由有两条:

**它确实发生过。** 转录是记录,而"我本来打算这么做,后来改了"是这段工作里最值得留下的一句话。
只留最后一版,就等于说它从一开始就是那么想的。

**页面上要看到的是当前那份。** 调研里最直接的一条教训:「计划作为普通消息出现在记录里、
agent 靠追加新消息执行它时,**原来那份计划就滚上去看不见了**」。所以页面把**本轮最后一条
计划活动**钉在看得见的地方。

**不建新表。** 当前计划是推导出来的,不是第二处存储 —— 和 `presence`、`working` 完全同构:
「读出来,从不存下来。存 online 就意味着离开时要写 offline,而被杀死的进程永远来不及写」。
一份计划存两处,就是两处会不一致。

### ③ 人不改 agent 的计划

调研里有「可编辑的计划」这种做法(「这是我打算做的 —— 要不要改改第 2 步?」)。**这里不做。**

理由是这个产品自己的立场:人把活**交出去**了。要改方向,说一句话就行 —— 那是这个产品已经
有的动作(打断并说新的),而且它留下的是一句人说的话,有名字有时间。而"人直接编辑了 agent
的计划"这件事,转录里没有位置放它,agent 那边也没有接口收它。

### ④ 计划变了要看得出来,但不刺眼

一份七步的计划改成八步,和"第 3 步做完了"是两件事,页面要分得开。但**不是每次勾掉一步都
弹一下** —— 调研里的四条反模式,第一条就是「默认展开完整过程,把真正的答案埋在过程细节
底下」。

所以:当前计划常驻可见且简洁(第几步/共几步 + 正在做的那步),完整列表可展开;**计划本身
被改写**时,转录里留一条看得见的线。

## 旅程

```
把一件多步骤的事交给 agent
  → 它开始工作,先给出计划          转录里一条"planned",页面顶部出现进度
  → 第 2 步做完                      进度变成 2/7,当前步换成第 3 步
  → 它发现漏了一件事,把计划改成 8 步  转录里再一条"planned",页面上是新的那份
  → 你半路进来看                     一眼看到 5/8 和正在做的那步,不用往上翻
  → 结束后回来看                     计划的每一版都还在转录里,按发生顺序
```

## 不做

- 不让人编辑 agent 的计划(见 ③)
- 不为计划建表(见 ②)
- 不要求 agent 必须有计划
- 不做跨轮次的计划:一份计划属于一个轮次,下一轮是新的一份
