# 把一件事交出去 —— 技术方案

`prd.md` 说的是「交办是一个开关,不是新建」。这份文件回答:那个开关在库里是什么,以及一轮做完
之后**谁决定下一步**。

**这一片几乎不加东西,它推广已经有的东西。** 一段对话、一条消息、一轮工作、长轮询、三态 ——
全部照旧。改的是一处判定、一个列名、三列。

---

## 一句话:一轮结束之后

```
03   一轮结束 → 没活了,等下一句问话
04   一轮结束 → 还有活,除非它在等,或者它完了
```

「有没有活」这个问题 `02` 就在问了(`whatIsOwed`),`03` 用「最后一句问话有没有人领」回答。
这一片把答案换掉,别的一律不动。

---

## 往回看一条

**不能只看最后一条。** agent 是在一轮**中间**跑那些命令的 —— 它说「我问你一件事」,然后那一轮
才收尾,于是最后一条永远是收尾。

所以规则是:**往回找最后一条决定下一步的行,跳过 `done` 和 `cancelled`。**

```
往回找到的那一条是                现在
──────────────────────────────────────────────────────
人说的话                          有活
handed-over  你把它交出去了        有活
handed-off   它开了一件子任务      有活 —— 开完接着做
handed-back  一件子任务有结果了    有活
它说的话 / 它跑的工具              有活
asked        它问了你一件事        等你
waiting-for  它说它在等子任务      等子任务
until        它在等一个时刻        时刻没到 = 等;到了 = 有活
failed / unknown  一轮出事了       等你
finish / taken-back               完了
```

**跳过的只有 `done` 和 `cancelled`。** 这两个是「这一轮结束了,而且没出事」,它们不说下一步是
什么;`failed` 和 `unknown` 说 —— 它们说「该有个人来看看了」。

**往回跳过的行最多一条**(一轮只有一个收尾),所以这是一次倒着走的索引扫描,读两行。

**没交办的那些对话,这张表不生效** —— 只有「人说的话」算有活,和 `03` 一个字不差。这就是那个
开关:开关合上,一轮做完它自己就有下一轮;开关不合,它做完就停在那儿等你。

---

## 一轮不再必须回答一句问话

`03` 的 `turns` 是 `(conversation_id, asked_seq)`,`asked_seq` 指向一条**问话**。自驱的一轮没有
问话可指。

**推广,不新建:`asked_seq` 从「这一轮在回答哪一句问话」变成「这一轮是从第几条之后开始的」。**

对 `03` 来说那一条就是问话,一个字都不用改;对自驱的一轮,那一条是上一轮的收尾。主键还是
`(conversation_id, seq)`,外键还指向 `messages`,一轮只能被领一次仍然由数据库裁决。

**列名跟着改:`asked_seq` → `after_seq`。** 一个名字讲两件事,就是两件事里有一件会被读错。

## 数据

`03` 的两张表不动,加三列:

```
conversations
  ...                              照旧
+ handed_over_at       timestamptz  从这一刻起它自己走。null = 现在没在交办中
+ parent_id            uuid null    开这件事的那段对话。null = 你开的
+ waiting_until        timestamptz  它在等的那个时刻。**这是一个索引,不是状态**
```

**「交办中」= `handed_over_at is not null`。结束就置空。** 一列而不是两列:开始的那一刻在
transcript 里那条 `handed-over` 上,结束的那一刻在 `finish` / `taken-back` 上,这一列只回答
「现在还在不在交办中」—— 而那正是列表页和 Inbox 唯一要按它筛的东西。

**为什么是列而不是一张 `tasks` 表。** 「一件事」和一段对话一对一,没有独立的身份,也没有独立的
生命周期 —— 它就是那段对话在某一段时间里的状态。`architecture.md` 那三条(独立身份 · 保护相邻
owner 表达不了的边界 · 当前就有消费者)一条都不满足,所以不建 owner。

**为什么 `handed_over_at` 不派生。** 派生要往回扫消息找最后一条 `handed-over` / `finish` /
`taken-back`,而 Inbox 要跨 Space 按它筛 —— 扫的量没有上界,也没法索引。同一条理由让
`machines.left_at` 也是一列。

**`waiting_until` 是一个索引,不是第二份真相。** 状态由上面那张表决定,而那张表里「等一个时刻」
读的是那条 `until` 活动自己带的时刻。这一列存在只为一件事:**叫醒器要能找出「谁到点了」而不用
扫全表** —— JSON 里的一个时间戳没法拿来当索引。**判定永远不读它。** 两者同一个事务里写,而且
只有一个会被读,所以它们没有分歧的机会。

`activityType` 加七个值。**不是 schema 改动** —— 那个槽本来就是开放的:

```
handed-over   从这里起它自己走
asked         它问了负责人一件事(带话)
handed-off    它开了一件子任务(带子任务的 id)
waiting-for   它说它在等子任务
handed-back   一件子任务有结果了(带它说的那句话)
until         它要等到什么时候(带时刻)
done          它说做完了                 ← 注意:和一轮的 done 同名不同层,见「三态出现在哪」
cannot        它说做不了,带原因
taken-back    你收回了
```

**不建**:`tasks` 表 · `state` 列(算出来的)· `wakes` 表 · 子任务的计数列(数一下就有)·
预算的任何一列。

## 决定

**① 到点不需要调度器,只需要有人叫醒**

「等一个时刻」看起来要一个定时任务。它不要。

因为**状态是算出来的**:时刻一到,那条 `until` 就过期了,这段对话不再是「在等」,而是「有活」。
没有任何东西需要在那一刻被触发 —— **需要被触发的只有那台机器,它正挂在长轮询上。**

所以服务器上一个循环,十秒一次:

```sql
select distinct machine_id from conversations
 where waiting_until <= now() and handed_over_at is not null
```

对每一台 `wakeMachine`。仅此而已 —— 它不写任何东西、不标记任何东西,**重复叫醒无害**,因为醒来
之后机器要么领走一轮(`takeOne` 顺手把 `waiting_until` 清空),要么发现没自己的事。

十秒的精度对「明天 12:00」和「每十分钟看一眼」都绰绰有余。多个实例各自 tick 会重复 wake,
一样无害 —— 那本来就是一条「去看看」。

**这是这一片唯一的新机制,而且它是一个叫醒器,不是一个调度器。** 真相在表里,和别处一样。

**② 开子任务和等子任务是两回事**

`hand-off` 之后它**接着做** —— 不然并行子任务开不出第二件。「在等」是它自己说的一句
`waiting-for`,单独一条命令。

任何一件子任务有结果,就往父的 transcript 追一条 `handed-back` 并叫醒父的机器。**哪怕它还在等
另外两件** —— 父 agent 醒来自己判断是接着等还是往下走。我们不替它数还剩几件。

**③ 同一台机器上的子任务排队,而且不会死锁**

一台机器一次只干一件事 —— `02` 就有的规则(`whatIsOwed` 里那句「有开着的轮次就什么都不派」),
一个字不用改。

父任务把活交给同一台机器上的另一个 agent,那件子任务要等那台机器空出来。而父任务正在等它 ——
死锁吗?**不。** 父任务写完 `waiting-for` 那一轮就收尾了,机器是空的,子任务当场被领走。

真正会排队的是**两件并行的子任务落在同一台机器上**:第二件等第一件做完。慢,但不会死。

**④ 一轮失败之后不自己重试,这条在服务端**

`prd.md` ⑥。做法不是「告诉 agent 别重试」——那是一条没有东西执行的规则。

做法是上面那张表里的一行:**一轮以 `failed` / `unknown` 收尾,这段对话就落到「等你」。**
机器领不到活,所以它连重试的机会都没有。**机械化,不是嘱咐。**

**⑤ 交办和说话是同一条路**

`POST .../hand-over` 做三件事,一个事务:

```
写一条 activity   handed-over
写一条 user 消息   你交办时说的那句话
set handed_over_at = now()
```

顺序和「打断」一模一样(活动在前、话在后),所以往回看到的是你说的话 → 有活 → `wakeMachine`。
`03` 的 `sayTo` 已经是这个形状,这里只多了一列一条。

**收回**同理:写 `taken-back`、`handed_over_at = null`、`wakeMachine`(让它别再等了)。

**⑥ agent 改状态走 CLI,不走 SDK 的工具**

它能做的五件事,五条命令:

```
handover task ask "…"                     问负责人一件事,然后等
handover task wait --until <时刻>          等到那时候
handover task wait                        等我开的子任务(任何一件有结果就叫醒我)
handover task hand-off "…" --to <agent>   开一件子任务,接着做
handover task finish --done | --cannot "…"
```

`handover task --help` 列得出来,所以**它自己会用**,不用我们把命令表塞进 prompt 里再指望它记住。
一级 `handover --help`、二级 `handover task --help`,后面加东西不用改前面。

**为什么是命令行不是 MCP 工具。** 命令行两家都认,而且不需要在任何机器上装任何东西 —— 它就是
那台机器上已经跑着的那个二进制。一个只有一家支持的工具协议,等于把这一片绑在一个厂商上。

**它凭什么能调?** 常驻进程起 agent 的时候把这段对话的 id 和一个只对这段对话有效的凭据放进
环境变量。命令拿着它调那四个机器端点 —— 和常驻进程自己写消息用的是同一扇门。

**⑦ 交办的时候要告诉它它被交办了**

不然它答完一句就停了,因为它不知道自己该往下走。

那一轮的输入里带上三样:**目标 · 到目前为止发生了什么(它自己就记得)· 你可以用这五条命令**。
第三样每一轮都带,不是只带一次 —— 一轮和一轮之间 agent 的会话可能接不上(`03` 决定⑨),
接不上的那一轮什么都不记得。

**⑧ 子任务的负责人是一个 agent,不是一个人**

`parent_id` 不为空 = 它的负责人是那段对话里的 agent。

于是 Inbox 只是一个查询:**交办中 · 在等你 · `parent_id is null`**,跨 Space 按你的成员资格过滤。
子任务问问题不会跑到你面前,不是因为我们过滤掉了,而是因为它问的本来就不是你。

子任务写 `asked` 的那个事务里,往父的 transcript 追一条 `handed-back`,并叫醒父的机器。

**⑨ 「完了」是真的完了**

`handed_over_at` 置空,这段对话就退回一段普通对话:它不再有活,你说话就是 `03` 的说话。

想让它再跑,再 `hand-over` 一次。**没有任何一条路能让一件结束的事自己又动起来** —— 唯一能给
`handed_over_at` 赋值的地方就是那一个端点。这是 `prd.md` ⑩ 的实现。

## 三态出现在哪

照旧,一处不动。一轮还是 `done` / `failed` / `unknown` 三种收尾,`cancelled` 还是单独一种。

**这一片新增的是「事」的状态,不是「轮」的状态**,而且两层同名的那个 `done` 要看清楚:

```
一轮 done       这一次它说完了,没出事
task done       它说这件事做成了
```

一轮 `done` 之后,交办中的对话继续有活;`task done` 之后它退回普通对话。**同一个词在两层里
表示两件事,是这一片最容易读错的地方** —— 所以 transcript 里那条 `done` 活动带 `activityType`
之外还要带一个「哪一层」,不能靠位置猜。

`cannot` 和一轮 `failed` 也要分清:

```
一轮 failed   一次尝试没成,再试一次是安全的
cannot        它判断这件事做不成,再试没有意义
```

两个词分开是有代价的(多一个概念),但合并的代价更大:一件因为一次网络抖动而 `failed` 的事被
记成「做不成」,就再也没人会去看它了。

## 接口

```
POST /spaces/{slug}/conversations/{id}/hand-over    交给它。body: { key, asked }
POST /spaces/{slug}/conversations/{id}/take-back    收回。body: { key }
GET  /me/inbox                                      跨 Space,所有在等你的事

POST /machines/current/conversations/{id}/asked     它问了负责人一件事
POST /machines/current/conversations/{id}/until     它要等到什么时候
POST /machines/current/conversations/{id}/hand-off  开一件子任务,回子任务的 id
POST /machines/current/conversations/{id}/waiting   它在等子任务
POST /machines/current/conversations/{id}/finish    done | cannot
```

五个机器端点各写一条 activity、各自 `wakeMachine`,和 `03` 那两个写入端点同一个形状。
`/me/inbox` 是唯一一个不在 Space 下面的读 —— 因为它跨 Space,这正是它存在的理由。

**长轮询、`stopWantedOn` 一个端点都不加,`takeOne` 换掉候选那一句。** `whatIsOwed` 的三步
(要不要停 · 忙不忙 · 领一个)一步都不动。

## 风险

**没有上限,而且我们知道。** 一个每轮都「成功」却在原地转圈的 agent,没有任何东西会拦它。这是
`prd.md` 里写明的选择:拿「每一步都看得见」换。这一片结束之后**先看真实数据** —— 一件事平均跑
几轮、最长的那件跑了多少 —— 再决定上限该记什么。凭想象定一个数,是给人一种有人在看着的错觉。

**Inbox 是唯一的刹车,所以它错一次的代价比别处大。** 一件在等你的事没出现在 Inbox 里,就是一件
永远不会再动的事。所以它是一个查询,而且是从和状态判定同一处规则算出来的 —— 两份实现总有一天
会不一致,而不一致的那一天你不会知道。

**「往回看一条」是这一片最容易腐坏的地方。** 今天跳过的只有两个值,而 `activityType` 是开放的:
以后每加一个活动,都要回答「它决定下一步吗」。加错一个,一件事要么卡住不动,要么自己动起来。
所以那张表是**一个函数**,不是散在几处的 if,而且每一行都有一个测试。

**子任务的深度没有硬限制。** 管住它的是「一件事底下同时最多四个 agent」这一个数,整棵树共享。
这个数够不够只有跑起来才知道,而它至少保证了「一晚上把笔记本填满」不会发生。

**「等一个时刻」的精度是十秒,而且不承诺。** 机器不在线的时候到点,它回来才动。这和整个产品
其他地方一致(机器不在就是不在),但对「上线后三小时观察数据」这种事,值得在页面上说清楚。

## 测试

```
交办一段聊过三句的对话 → 它接着往下走,没有第二段对话被建出来
一轮 done 之后 → 它自己又被派了一轮,不用任何人说话
一轮 failed 之后 → 它没有被再派活,那件事在等你
一轮 unknown 之后 → 同上
一轮 cancelled 之后(你打断了)→ 往回看到你那句话,接着走
它写 asked,那一轮再收个 done → 还是「等你」,收尾没有把它盖掉
你回一句 → 当场被派活
它写 until(两秒后)→ 两秒内没活;两秒后叫醒器把它叫起来
它写 until,然后你说话 → 当场醒,不等那个时刻
它 hand-off 之后没有 waiting-for → 还有活,能接着开第二件
它 hand-off 两件再 waiting-for → 在等;第一件回来就醒
子任务的 asked → 进的是父的 transcript,不是你的 Inbox
两件子任务落在同一台机器 → 第二件排队,不是并行,而且不死锁
finish 之后 → 不再有活;你说话就是普通的说话
收回 → 不再有活;已经写下的一条不少
再交办一次 → handed_over_at 重新有值,transcript 里两次都在
一台机器上两件交办中的事 → 一次只跑一件
叫醒器跑两遍 → 同一轮不会被领两次(turns 的主键)
没交办的对话,一轮 done 之后 → 没活。这一片一个字都没改到 03
```
